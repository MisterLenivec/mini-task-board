# Процесс разработки

## Этапы и разрешения

1. **Локальная инициализация (завершена и принята).** Документы, AGENTS.md, конфигурации ролей и Codex, каркас, настройки Ruff/pytest, локальный Git, начальный коммит main и dev от него. Без зависимостей, приложения, удалённого репозитория и авторизации. После отчёта — обязательная остановка для проверки пользователем.
2. **GitHub (подключён, первый push разрешён и выполнен).** Установка gh официальным поддерживаемым способом с системными разрешениями; gh auth status для github.com; при необходимости браузерный gh auth login, вход подтверждает пользователь. Не запрашивать пароли/токены, не выводить секреты. Показать GitHub login. Перед созданием репозитория подтвердить владельца, mini-task-board и public. Перед первым push отдельно показать точный URL, ветки и коммиты и получить разрешение. Создавать пустой репозиторий без автоматического push. HTTPS и credential helper при необходимости настраиваются только локально. Защиту веток и обязательные CI checks настроить после появления реального workflow.
3. **Функциональность.** Последовательность feature/project-foundation → feature/task-api → feature/board-ui → feature/drag-and-drop. Foundation: зависимости, минимальное приложение, проверки и настоящий CI. Затем контракт и SQLite; затем UI со списком статусов; затем перетаскивание. Каждая ветка от актуальной проверенной dev.
4. **Проверки и интеграция.** Повторяется для каждой feature. Локальные проверки → tester → независимый reviewer → CI → merge в dev → повторная проверка dev.
5. **Финальная проверка dev и ручная приёмка.** Полный прогон, реальные HTTP, браузер, перезапуск с сохранением данных, команды WSL2 и проверка адреса в браузере Windows. Остановка для приёмки пользователем.
6. **Выпуск.** Подготовить PR dev → main, показать SHA и состав. Merge только после отдельного явного разрешения пользователя на этот результат; при изменении состава согласовать снова. Проверить main, синхронизировать main обратно в dev через PR и проверить dev.

## Ветки и коммиты

main — стабильная ветка по умолчанию. Разрешение этапа 1 покрывает первоначальный коммит. После инициализации любые изменения main требуют отдельного явного разрешения. dev — интеграционная ветка. Код в main/dev напрямую не коммитить после начальной инициализации.

Координатор самостоятельно создаёт feature-ветки, коммиты и PR и переключается между ветками в разрешённом объёме. Для MVP одна feature-задача за раз; не переключать общую рабочую директорию при работающем агенте. Не выполнять force push, reset --hard, clean и другие опасные операции без согласования. Не изменять другие репозитории. main/dev защищаются PR, CI, актуальностью веток, запретом force push и удаления; локально эти ограничения являются правилами процесса, серверная защита появляется только на GitHub.

Feature → dev: squash merge. dev → main: merge commit с разрешением пользователя. После выпуска main синхронизируется обратно в dev через PR, сохраняя историю долгоживущих веток.

## Обязательные условия автоматического merge в dev

Все условия одновременно:

1. Реализация завершена в согласованном объёме.
2. Все применимые локальные проверки реально выполнены и успешны.
3. tester подтвердил функциональность и критерии готовности.
4. Независимый reviewer завершил review; блокирующих замечаний нет.
5. GitHub Actions CI успешно завершился.
6. Feature актуальна относительно dev, конфликтов нет.

Результаты tester/reviewer и проверок привязаны к head SHA feature и базе dev. После изменения кода или базы актуализировать проверки и review. Перед merge проверить ожидаемый head SHA, использовать --match-head-commit. Не обходить защиту через --admin. Не включать отложенный auto-merge до завершения всех проверок.

При одном аккаунте отчёт агента reviewer не является GitHub approval другого пользователя. Автор PR не может одобрить свой PR. Независимый отчёт фиксируется в PR и проверяется координатором; обязательный второй GitHub-аккаунт в MVP не требуется.

После каждого merge полный локальный прогон на новом SHA dev и CI на push dev. Ошибка останавливает дальнейшую интеграцию. Исправление через отдельную feature-ветку с теми же проверками.

## Команда

Координатор ставит ограниченные задачи, вызывает backend/frontend/tester/reviewer, собирает результаты и управляет Git. Роли определены в .codex/agents/*.toml. Соблюдать лимит .codex/config.toml и текущей сессии; не держать простаивающие запуски. Модель и effort наследуются. Независимый reviewer не автор проверяемого кода и не исправляет его во время review.

Конфигурации — постоянные инструкции, запуски агентов создаются по задачам. Они не дают отдельной песочницы и не расширяют разрешения родительской сессии. При недоступности роли или проверки явно сообщать ограничение; не подменять независимый review самопроверкой. Собственные Skills пока не создаются.

## Проверки и CI

Позднее локально и в CI: Ruff check, Ruff format --check, pytest API/интеграция, pytest-playwright Chromium после появления UI. Настройки в pyproject.toml. Настоящий workflow создаётся в feature/project-foundation: PR в dev/main и push dev/main, Python 3.12, минимальные read-only права workflow. Применимые проверки не должны скрываться за skip/xfail, continue-on-error или пустым набором тестов.

Запускать Uvicorn с временной БД; проверять API настоящими HTTP-запросами. Браузерные тесты работают с настоящим сервером. Проверять CRUD, фильтр, смену статуса списком и drag-and-drop, ошибки API, безопасный текст, сохранение после перезапуска. Тесты никогда не используют data/task_board.sqlite3.

Каждая проверка имеет статус: успешно / ошибка / неприменима с причиной / не выполнена или недоступна. Пропущенная применимая проверка блокирует merge. На этапе 1 Ruff, pytest, HTTP, Playwright и CI ещё не выполняются: зависимости и реализация отсутствуют. Проверять документы, TOML, обнаружение ролей, структуру, git diff --check, ignore-правила и Git-состояние; привлекать tester и reviewer для этих аспектов.

## Изоляция

Только личный GitHub, единственный будущий origin — github.com/<подтверждённый личный владелец>/mini-task-board. Проверять fetch/push URL. Рабочий GitLab, рабочие SSH-ключи и его авторизация не используются и не изменяются. Git identity только через --local. Глобальные Git/SSH-настройки не менять. Секреты не читать и не публиковать; пароли/токены в переписке не запрашивать. Не запускать gh auth token или вывод токенов.

Пользователь разрешил весь MVP и автоматический переход между feature-задачами при соблюдении проверок. Обязательная остановка — финальная dev и ручная приёмка. main после первой публикации cadd2cd92ac9b79ba69df3277b28344832559561 не изменять. Пользовательские настройки агентов сохранены отдельным коммитом dev. Git identity в этом репозитории использует подтверждённый GitHub noreply; личный email в отправляемой истории отсутствует.
