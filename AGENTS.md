# Mini Task Board: постоянные инструкции

## Разрешённый объём

Пользователь разрешил полную реализацию согласованного MVP, установку зависимостей в .venv, feature-ветки, PR и автоматическую интеграцию в dev после всех проверок. Этапы инициализации и подключения GitHub завершены. Продолжать между feature-задачами самостоятельно. Остановиться после финальной проверки dev для ручной приёмки. После первоначальной публикации main менять или сливать в неё запрещено без отдельного явного разрешения. Собственные Skills не создавать.

## Источники решений

Читать README.md, docs/architecture.md, docs/api-contract.md и docs/development-workflow.md. Сохранять минимальный MVP: Python 3.12, FastAPI, синхронный SQLAlchemy 2, SQLite, Pydantic v2, HTML/CSS/vanilla JS. Не добавлять технологии и архитектурные слои без необходимости и согласования изменения архитектуры. Пользовательские данные не удалять.

## Команда

Координатор распределяет задачи и управляет интеграцией. Использовать специализированных субагентов по .codex/agents/*.toml: backend — API/БД; frontend — UI/JS; tester — независимые проверки и регрессии; reviewer — независимый Code Review. На каждой интеграции обязательны tester и reviewer. На этапе инициализации они проверяют применимые документы, настройки и Git, без реализации приложения.

Давать агентам ограниченный объём, критерии готовности и базу сравнения. Reviewer не должен быть автором реализации и не исправляет проверяемые файлы. Tester может добавлять тесты в разрешённых этапах; после этого проверки и review должны соответствовать итоговому SHA. Не переключать Git-ветки при работающих в общей директории агентах. Один автор изменений за раз; независимые проверки можно выполнять параллельно. Использовать лимит из .codex/config.toml в пределах возможностей текущей сессии. Недоступность агента явно сообщать; самопроверка не заменяет независимый review.

## Git

Этап 1 разрешает initial commit main и создание dev от него. Затем main изменяется исключительно после отдельного явного разрешения пользователя. Feature-ветки создавать от актуальной проверенной dev. Коммиты, PR и обычные переключения выполнять самостоятельно в разрешённом объёме.

Автоматический squash merge feature/* → dev разрешён только когда: реализация закончена; все применимые локальные проверки успешны; tester подтвердил критерии; независимый reviewer не имеет блокирующих замечаний; CI успешен; ветка актуальна и без конфликтов. Фиксировать head/base SHA. После изменений повторять соответствующие проверки и review; перед merge проверять ожидаемый head SHA. Пропущенная, недоступная или не запущенная применимая проверка не является успешной.

После каждого merge повторять локальные проверки и CI на интегрированной dev. При ошибках остановить интеграцию и исправлять отдельной feature-веткой. Выпуск dev → main через PR с merge commit только с отдельным разрешением на конкретный результат. После выпуска синхронизировать main обратно в dev через PR и проверить dev.

Не делать force push, не обходить защиту через --admin, не выполнять опасные Git-операции без согласования. Не менять другие репозитории. Серверная защита веток появляется на GitHub позднее; правила в документах сами по себе не являются технической защитой.

## Проверки

После реализации: python -m ruff check ., python -m ruff format --check ., python -m pytest из .venv. Дополнительно запускать приложение и проверять API реальными HTTP-запросами; после появления UI запускать pytest-playwright Chromium. SQLite-файлы тестов только временные; пользовательскую БД не использовать. Проверять сохранение после перезапуска, ошибки API, валидацию, безопасный вывод текста и регрессии.

Отчитываться по фактическим результатам: успешно, ошибка, неприменима с причиной, не выполнена/недоступна. Не скрывать отсутствующие тесты через пустые заглушки, skip/xfail или continue-on-error. На этапе 1 не запускать отсутствующие Ruff/pytest и не называть их успешными: выполнять статические проверки документов/TOML, обнаружения ролей и Git.

## Безопасность и доступ

Только личный GitHub. Запрещены использование и изменение рабочего GitLab, его авторизации и рабочих SSH-ключей. Не менять глобальные Git/SSH-настройки. Identity задавать только локально и только с подтверждёнными личными данными. Не читать и не публиковать секреты, не запрашивать пароли/токены в переписке.

На этапе GitHub системные разрешения запросить перед установкой gh; пользователь подтверждает браузерный вход. Показать аккаунт. Перед созданием remote подтвердить owner/name/visibility; перед первым push отдельно показать точный URL/ветки/коммиты и получить разрешение. На этапе 1 никаких сетевых Git-операций.
